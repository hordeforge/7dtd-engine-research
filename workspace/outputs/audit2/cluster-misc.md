# Audit: raycast-pathing.md, dedicated-misc-systems.md, dedicated-leftovers.md (V3.0.1 stable DLL)

**Verdict:** All big structural claims hold (drone-only raycast pathing, debug-only flood fill, Discord reclassification of AuthAndLoginManager, WireManager/ItemActionEntry client calls), but one "verified client-only" entry is wrong in a way that matters: WorldStats-derived DensityScore steers server-side RWG prefab placement (1 CRITICAL, 2 MAJOR, 4 MINOR).

All commands below use:
`ASM="/home/maci/.local/share/Steam/steamapps/common/7 Days to Die Dedicated Server/7DaysToDieServer_Data/Managed/Assembly-CSharp.dll"`

Tooling caveat discovered during this audit (affects how the docs' own evidence
claims should be read): `FindCallers.exe` ignores its third argument. Disassembly
of the tool (`ikdasm tools/bin/FindCallers.exe`) shows it reads only `args[1]`
and substring-matches it against each callee `MethodReference.FullName`
(`IL_0009: ldarg.0 / ldc.i4.1 / ldelem.ref` is the only argument load besides the
assembly path). Per-method caller claims therefore require manual filtering of
the output, and field reads (`ldfld`/`stfld`) are invisible to it entirely. Both
gaps produced findings below.

---

## Findings

### [F1] CRITICAL: dedicated-misc-systems.md, "Out of scope (verified client-only)" / WorldStats

**Claim:** "the numbers are editor telemetry (`CaptureWorldStats`, `XUiC_Editor*`); nothing server-side reads them."

**Ground truth:** `PrefabData.Init` reads `WorldStats.TotalVertices` to compute
`PrefabData.DensityScore`, and RWG (which the dedicated server runs when
generating a world) reads that field to select and budget prefabs:

- `mono tools/bin/DumpMethod.exe "$ASM" PrefabData Init`:
  `IL_0149: callvirt System.Int32 WorldStats::get_TotalVertices()` ...
  `IL_015A: conv.r4 / IL_015B: stfld Single PrefabData::DensityScore`
  (i.e. `DensityScore = (TotalVertices + 50000) / 100000`).
- `ikdasm "$ASM" | grep -n "PrefabData::DensityScore"` finds `ldfld` reads at
  lines whose enclosing methods are
  `WorldGenerationEngineFinal.PrefabManager::GetPrefabWithDistrict` (line
  2349515) and `WorldGenerationEngineFinal.StreetTile::SpawnMarkerPartsAndPrefabs`
  / `UpdateDisplay` (lines 2360676-2361691), plus editor-side
  `PrefabPreviewManager/PrefabGameObject`. `SpawnMarkerPartsAndPrefabs` even
  takes a `float32 totalDensityLeft` parameter, i.e. a density budget fed by
  these numbers.

`FindCallers` could not see this because `DensityScore` is a field
(`FindCallers "$ASM" DensityScore x` returns nothing); the doc's caller-walk
methodology was structurally blind to field reads. WorldStats participates in
dedicated RWG behavior and must not sit under a "verified client-only" heading.

**Fix:** Move WorldStats out of the client-only list; document the
`TotalVertices -> PrefabData.DensityScore -> RWG PrefabManager/StreetTile`
flow (cross-link world-generation.md), and add a methodology note that
FindCallers misses field accesses.

### [F2] MAJOR: dedicated-misc-systems.md, §CompanionGroup

**Claim:** "the group is the server's record of which allied entities (companions/minions) belong to a player", presented under a preamble stating every type "was confirmed dedicated-relevant by walking its callers back to server-side systems".

**Ground truth:** `CompanionGroup.Add` and `CompanionGroup.Remove` have **zero
call sites in the entire assembly**. `mono tools/bin/FindCallers.exe "$ASM"
"CompanionGroup::" x` returns only `EntityPlayer::get_Companions -> .ctor`
(lazy construction) and `XUiC_CompanionEntry*` reads;
`ikdasm "$ASM" | grep "CompanionGroup::"` confirms `Add`/`Remove` appear only
at their definitions. In V3.0.1 the group can never be populated: it is a stub
for an unshipped feature, and the only real consumers are client UI. The
"server's record" framing is inference from `EntityPlayer` living server-side,
not a caller-verified fact; as written the section is padding.

**Fix:** Reword to "constructed lazily, never populated in V3.0.1 (Add/Remove
have no callers); reserved surface for the companion feature" or move it to the
out-of-scope list.

### [F3] MAJOR: dedicated-leftovers.md, "Out of scope (verified client-only)" / BuffEntityUINotification

**Claim:** "HUD buff notification generated by `PlayerEntityStats`; client HUD" listed under "verified client-only".

**Ground truth:** the constructor runs on the dedicated server, unconditionally,
in the authoritative buff path:

- `mono tools/bin/FindCallers.exe "$ASM" "EntityBuffAdded" x`:
  `EntityBuffs::Tick -> EntityStats::EntityBuffAdded` and
  `EntityBuffs::Read -> EntityStats::EntityBuffAdded` (server buff tick).
- `mono tools/bin/DumpMethod.exe "$ASM" PlayerEntityStats EntityBuffAdded`:
  no dedicated/local-player gate; for any non-hidden iconed buff it executes
  `IL_0046: newobj System.Void BuffEntityUINotification::.ctor(EntityAlive,BuffValue)`
  and `List<EntityUINotification>::Add` into `m_notifications`.
- Consumers of the list are only `XUiC_ActiveBuffList`/`XUiC_BuffPopoutList`
  (`FindCallers "$ASM" "get_Notifications" x`), so the object is behaviorally
  inert headless, but it is constructed and retained per buff add on every
  server-side `EntityPlayer`.

Graded MAJOR rather than CRITICAL because no server behavior depends on it
(allocation-only); under a strict reading of "client-only type that actually
runs on the server" it could be argued CRITICAL, which is exactly why the
wording should change.

**Fix:** Reword to "constructed server-side in `PlayerEntityStats.EntityBuffAdded`
(no gate) but consumed only by HUD controllers; inert allocation on dedicated."

### [F4] MINOR: dedicated-misc-systems.md, §GameStageGroup

**Claim:** "`SleeperVolume` and `PrefabVolumes.PrefabSleeperVolumeList` resolve a volume's gamestage group via `TryGet`".

**Ground truth:** `mono tools/bin/FindCallers.exe "$ASM" "GameStageGroup::" x`
shows `TryGet` called only from `SleeperVolume::UpdateSpawn` (twice);
`PrefabVolumes.PrefabSleeperVolumeList::ReadFromProperties` calls only
`CleanName`. Server relevance stands; the caller attribution for TryGet is
half wrong.

**Fix:** "SleeperVolume.UpdateSpawn resolves via TryGet; PrefabSleeperVolumeList
normalizes names via CleanName."

### [F5] MINOR: dedicated-misc-systems.md, WireManager bullet

**Claim:** "the sole gameplay caller `TileEntityPowered.DrawWires` early-outs..."

**Ground truth:** `mono tools/bin/FindCallers.exe "$ASM" WireManager x` lists
additional callers: `TileEntityPowered::RemoveWires`,
`ItemActionConnectPower::StartHolding/StopHolding/OnHoldingUpdate/DisconnectWire`,
`AutoTurretController::Init/Cleanup`, `MotionSensorController::Init/Cleanup`,
`XUiC_CameraWindow::OnClose`, `GameManager::SaveAndCleanupWorld`. All are
client-visual or lifecycle paths, so the classification stands, but "sole
gameplay caller" is false. The `DrawWires` early-out itself is confirmed:
`DumpMethod "$ASM" TileEntityPowered DrawWires` shows
`IL_0001: get_BlockTransform / IL_0007: op_Equality / IL_000C: brfalse.s IL_0016 / ... IL_0015: ret`.

**Fix:** Enumerate the caller set or say "all callers are client visual paths".

### [F6] MINOR: dedicated-leftovers.md, BlockSwitchController bullet

**Claim:** "The one server-side toucher, `TriggerManager.CheckPowerState`..."

**Ground truth:** `mono tools/bin/FindCallers.exe "$ASM" "BlockSwitchController" x`
also shows `BlockActivateSwitch::Refresh`, and Block classes execute
server-side. It is null-guarded the same way
(`DumpMethod "$ASM" BlockActivateSwitch Refresh`: `IL_007A: GetBlockEntity /
IL_0081: brfalse.s`, `IL_0092: GetComponent<BlockSwitchController> /
IL_00A0: brfalse.s`), so the classification stands; the enumeration is
incomplete.

**Fix:** "Both server-side touchers (TriggerManager.CheckPowerState,
BlockActivateSwitch.Refresh) null-guard the GetComponent."

### [F7] MINOR: dedicated-misc-systems.md, RaidEvent/BitsUsedEvent bullet

**Claim:** "Twitch EventSub payload DTOs consumed only by `Twitch.TwitchManager`".

**Ground truth:** true for `BitsUsedEvent`
(`FindCallers "$ASM" "BitsUsedEvent::" x` -> only `Twitch.TwitchManager`), but
`RaidEvent` is also touched by `TwitchActionsFromXml::ParseEvent`
(-> `TwitchEventPreset::AddRaidEvent`) and `XUiC_OptionsTwitch::get_HasRaidEvents`.
Still entirely the streamer-client Twitch family; classification stands,
"only" does not.

**Fix:** "consumed only inside the Twitch client stack (TwitchManager,
TwitchActionsFromXml presets, options UI)".
